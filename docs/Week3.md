## Exit Ticket（第3回の振り返り）

1. **プロンプトを「仕様」として考えるうえで大事だと思ったこと**
   「誰向けか（対象者）・どの地域や場面か・出力形式・根拠や出典・危険な断定の回避」を明示すること。これらが曖昧だと再現性が低く、防災判断に使えない一般論しか得られないため、仕様として条件を具体的に固定することが鍵になる。

2. **自分が試したプロンプト条件3つ**
   ① 条件なし ② 役割指定 ③ 出力形式指定（さらに任意で、評価基準付き・few-shot例付き・安全性/断定回避条件付きも試した）。

3. **最も改善した条件と、その理由**
   出力形式指定（箇条書き＋見出し）。条件なしでは抽象的だった出力が項目ごとに整理され、視認性と目的適合性が大きく向上し、高齢者が必要な情報を探しやすくなったため。最終的にはこの形式指定に役割指定・安全性条件を統合して5観点を同時に引き上げた。

4. **まだ残った問題・リスク**
   LLMは実際の避難所の開設・収容状況、個人の身体状況や移動手段、地域固有のハザードマップ情報を把握できない。安全性を意識して断定を避けすぎると緊急時にかえって迷いを生む懸念や、出力の根拠・出典が曖昧なままになる問題も残った。

5. **都市・防災情報で、プロンプトだけでは不十分だと思った点**
   現在の浸水リスク・避難所の開設/収容状況・リアルタイムの気象警報など、動的で地域固有の情報はLLM単体では取得できない。公式ハザードマップの正確な解釈や要支援者の個別状況も担保できず、最終判断には公式情報の確認が不可欠。

6. **第4回のAIエージェント設計で、LLM以外に必要になりそうな要素**
   外部データ（気象庁・自治体の公式情報やハザードマップAPI）、ツール呼び出し（避難所開設状況・浸水リスク・最新警報の取得）、人間確認（要支援者の個別対応は福祉/介護担当者や家族による確認）、出力を検証する評価とログの仕組み。
